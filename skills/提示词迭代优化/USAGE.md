# 提示词迭代优化 · 使用文档（v2.3）

> 本文档讲「怎么用这个技能」，不是讲脚本怎么跑。你不需要知道底层 Python 引擎，
> 只要像平常一样把需求说给 WorkBuddy 听，它会在合适的时候加载本技能并完成优化。

## 1. 这个技能能帮你做什么

把一段"弱"提示词（口语化、缺角色、缺步骤、含模糊词、结构混乱）升级成
**结构化、可落地、角色清晰、约束明确**的高质量提示词（默认 LangGPT 风格）。

你最终得到三样东西：

1. **优化后的提示词本身**（可直接复制去用）
2. **一份报告**（原提示词的问题、改前 / 改后评分、G1–G10 门禁结论）
3. **一份可视化报告 `report.html`**（v2.2 起）：每轮**改了什么 + 改进评价**，
   以及**完整运行跟踪**——每轮跑的命令、交给子代理的任务卡原文、子代理的产出原文

底层由"确定性诊断引擎（零 LLM）+ 代理 / 子代理改写 + 独立盲评"组成，但对你完全透明。

## 2. 怎么开始（一句话入口）

不需要任何命令。直接对 WorkBuddy 说类似的话即可：

- "帮我优化这段提示词：<粘贴你的提示词>"
- "把下面这个 system prompt 写得更结构化"
- "我的提示词效果不好，帮我改改：<...>"
- "对比一下这两个提示词哪个更好"
- "给这个提示词打个分 / 做个诊断"

只要语义命中「优化 / 改写 / 改进提示词 / 提示词工程 / 结构化提示词」，技能就会被触发。

### 先弄清一件事：不是所有场景都会多轮迭代

迭代与否**不看场景，看走哪条执行路径**。11 个场景分三类：

| 类别 | 场景 | 迭代 | 子代理 | 强制盲评 |
|---|---|---|---|---|
| **A 走完整协议管线** | 一、四、七、八 | ✅ 有剩余问题才继续<br>（结构循环默认上限 2 轮，可设 3；<br>全局迭代上限默认 5 轮，可 --max-iterations 指定） | ✅ 每轮一个 | ✅ 收敛后必过 G10 |
| **B 纯确定性单命令** | 二、三、九（及 lint / vars） | ❌ 0 轮 | ❌ 不起 | ❌ 无 |
| **C 单次生成式接缝** | 五、六（含红队审稿） | ❌ 0 轮 | ✅ 一次 | ❌ 无 |
| **D 非优化流程** | 十（下游使用）、十一（回看报告） | — | — | — |

判定规则（`run_pipeline.py`，纯代码逻辑）：

```text
第 1 轮改写后 → 还有 issues 且未达结构轮数上限 → 进第 2 轮（iterate_directed 定向修改）
             → issues 清零               → 直接进盲评（不迭代）
             → 连续 2 轮 delta < 5 或达结构轮数上限 → FAIL
盲评发现 blocking_conflicts → 有界冲突返工（仅 1 次；二次冲突即 FAIL）
盲评 < 质量目标(85) 且无冲突 → 质量返工（默认 2 次；计入全局迭代上限）
全局最大迭代次数达上限（默认 5，可 --max-iterations 指定；结构循环+返工合计）
             → 强制终止，交付历史最优轮（Plan A 选优）
最终交付：盲评分最高且无 blocking_conflicts 的那一轮（Plan A 选优），而非最后一轮
```

所以：**A 类场景也不保证多轮**——第 1 轮就把问题清干净的话，只有 1 轮；
反过来，本次实战跑了 7 轮，是因为轮数上限设成 3 + 盲评返工 +1 + 确认可修后手工加轮。

### 场景一：优化一条提示词（system / user）

- **触发**："优化这段提示词：<内容>" 或 "把下面 system prompt 结构化"。
- **技能动作**：
  1. 诊断原始提示词（确定性引擎，零 LLM）：找模糊词、缺角色、缺步骤、缺约束。
  2. 按 LangGPT 骨架改写（生成式接缝，由脚本派发任务卡、**独立 fulfil 子代理**执行）。
  3. 收敛后**强制盲评**：第二个无上下文 judge 子代理只看终稿独立打分（G10 门禁）。
  4. 评分对比：改前 vs 改后。
- **你得到**：改写后的提示词 + 报告（如本次实战 **70 → 96 分**）+ 盲评结论
  + 可视化报告 `report.html`。
- **可选补充**：说明 mode（system 还是 user）、目标平台、受众、禁忌，能得到更贴身的版本。
  **收口需求时技能会问你这两个问题**：目标场景是什么、助手的工作方式（先诊断再改写 /
  直接给稿 / 对话式）——答得越具体，终稿越贴身。

**真实例子**（实跑记录 · run `20261007-171758`）

输入 `raw_resume_coach.txt`（157 字符，**70 分**，3 条问题）：

```text
帮我改简历。
你是一个帮人改简历的 AI 助手。我把简历发给你，你帮我改一改，让 HR 更容易看中。
简历：{{简历原文}}
岗位：{{目标岗位JD}}
要求：- 表达专业一点 - 尽量用数据说话 - 可以用 STAR 法则
     - 不要太夸张，不要编造我没做过的经历 - 顺便给点建议
```

实际结果：终稿 **96 分**、25113 字节、G1–G10 全 PASS；两个中文占位符完整保留。
跑的过程就是三步（`--dispatch` 渲染任务卡 → 子代理改写 → `--resume` 校验），
最终产物见下一节的报告。

### 场景二：只做诊断体检（先不改写）

- **触发**："先诊断一下这个提示词有什么问题" / "给我做个提示词体检"。
- **技能动作**：只跑分析接缝，返回 issues / score / suggestions。
- **适用**：你想先看懂问题、自己改，或批量筛掉差提示词。
- **你得到**：问题清单 + 评分 + 改进方向，不动原提示词。

**真实例子**（实测输出，原样粘贴）

```json
{
  "issues": [
    "含模糊词「尽量」，建议量化为具体可执行标准",
    "缺少角色 / 身份设定（建议用 LangGPT 风格明确 # Role）",
    "缺少明确的执行步骤 / 工作流"
  ],
  "score": 70,
  "patch_plan": [
    { "target": "含模糊词「尽量」…", "action": "针对问题：含模糊词「尽量」…" }
  ]
}
```

`patch_plan` 就是后续改写要逐条落实的指令——诊断结果直接驱动下一轮改写。

### 场景三：对比两条提示词（A/B 评审）

- **触发**："对比这两个提示词哪个更好" / "我改了一版，看看有没有变好"。
- **技能动作**：对前后两条分别评分，做结构化对比。
- **你得到**：winner（before / after / tie）、分差 delta、理由 reason。
- **适用**：验证一次改写是否真的有效，决定要不要采纳。

**真实例子**（实测输出）

```json
{
  "winner": "after",
  "delta": 26,
  "reason": "优化后结构评分 96 高于优化前 70，提升 26 分"
}
```

> ⚠ 此 JSON 是 `compare` 确定性命令的**内部结构诊断衬底**（上游无对应机制），
> `delta`/`score` 仅为内部诊断值，**不是质量分**——质量分唯一来源是盲评 judge
> 的 0-100 / overall（2026-10-10 与上游对齐后，报告与日志不再呈现结构分）。

### 场景四：多轮迭代优化

- **触发**："再迭代优化两轮" / "一轮不够，继续改"。
- **技能动作**：v2.1 采用「出题—答题—判卷」乒乓协议 + 强制盲评：脚本诊断出剩余问题
  （issues），自动转为改写指令（patchPlan）渲染成子代理任务卡（`--dispatch`）；
  每轮由**独立 fulfil 子代理**按 `iterate_directed` 模板对上一轮终稿做**融合修改**
  （改需求点、不动其余），脚本再校验、评分。收敛后由**盲评 judge 子代理**终审，
  发现硬伤（blocking_conflicts）会自动回灌一次有界冲突返工。直到 issues 清零、
  分数停滞或达到结构轮数上限（默认 2，可至 3；冲突返工自动 +1）。全局另有「最大迭代次数」硬上限（默认 5，可用 --max-iterations 指定），结构循环与所有返工合计计入，达上限即终止并交付历史最优轮。
- **你得到**：每轮的评分递进 + 盲评结论（`runs/<ts>/report.json` 留档可复现）、
  G1–G10 门禁全过的最终版本，以及逐轮 diff 与改进评价的可视化报告。
- **适用**：复杂提示词一次写不到位，需要逐步打磨。
  - **注意**：协议对「致命自洽冲突（blocking_conflicts）」只给**一次**有界返工，二次冲突会判 FAIL——这是防死循环的闸门，不代表缺陷不可修（此时应显式加轮并重新盲评）。
    盲评未达质量目标（默认 85）但**无致命冲突**时，触发「质量返工」，默认最多 2 次（回弹 2 轮再判），计入全局最大迭代次数。
  - **最终交付哪一轮（Plan A 选优）**：多轮迭代中若末轮分数反低于前轮，技能**不会盲目交付最后一轮**——任何终态（PASS / FAIL / 达迭代上限）都会自动挑「盲评分最高且无 blocking_conflicts」的那一轮作为交付物；该轮全文写入报告并展示在 `report.html`，同时 `last_final`（最后一轮）原样留档。无合格盲评记录时退回最后一轮。

**真实例子**（实跑记录 · run `20261007-171758`，7 轮 + 4 次盲评）

分数轨迹（旧口径结构分，2026-10-10 前的历史实跑记录，仅作示例留存；现行报告不再呈现结构分）：`70 → 86 → 86 → 96 → 96 → 76 → 96`

| 轮次 | 变化 | 报告给出的改进评价 |
|---|---|---|
| r1 | 70 → 86 | 有效改进（补角色、步骤、量化口径） |
| r2 | 86 → 86 | 空转（幂等，未带来变化） |
| r3 | 86 → 96 | 有效改进（"相关度"改为可计数口径） |
| r5 | 96 → **76** | **退步** ⚠ 报告自动提示"先查规则器假阳性" |
| r6–r7 | 76 → 96 | 有效改进（冲突修复完成） |

4 次盲评依次抓出 **5 / 2 / 1 / 0** 条 blocking_conflicts。其中一条真实硬伤是：
「要求每条 bullet 写完整 STAR 四要素（5–7 句）」与「单条 bullet ≤60 汉字」在字数上
不可能同时成立——**这类问题规则引擎和分数都发现不了，只有盲评和真实用例抓得住**。

### 场景五：创意增强 / 多视角变体（生成式）

- **触发**："给个更有创意的版本" / "从另一个角度重写"。
- **技能动作**：这是生成式接缝，没有规则化替身，会由主代理直接产出，
  或 spawn 子代理（挂强约束 prompt 模板）来 fulfil，保证只产出最终提示词。
- **你得到**：一个不同于基础改写的创意变体。
- **注意**：这是"生成式"结果，质量取决于代理 / 子代理，建议人工确认后使用。

**真实例子**（子代理实跑产出 · 节选）

同一份"帮我改简历"需求，常规改写是「简历顾问」，创意变体换成了**招聘方视角**：

```markdown
# Role
简历逆推改写官 —— 招聘决策还原师

## Profile
你不是简历顾问，而是招聘方那一侧的人。先还原 HR 在 8 秒初筛、面试官在 30 分钟
深挖时分别会看什么、跳过什么、追问什么，再据此重写简历。

## Workflows
1. 拆 JD：把 {{目标岗位JD}} 拆为硬性门槛、核心职责、加分项三类
2. 建对照表：{{简历原文}} 逐条经历 → 对应哪类要求 → 命中 / 未命中 / 证据不足
3. 定淘汰项：列出 HR 在 8 秒内会因之淘汰的 3 个具体问题
4. 改写  5. 抗辩预演：为最强的 2 条经历各写 1 个面试官追问与回答口径
```

### 场景六：按平台 / 模型 / 语种定制

- **触发**："改成适合小红书的语气" / "针对 Claude 改写" / "英文版 LangGPT"。
- **技能动作**：把你的定制约束（平台调性、模型偏好、输出语言、长度）写进 `## Constraints` 等节。
- **你得到**：带定制边界的结构化提示词。
- **提示**：约束越具体（"每段 ≤120 字、不用空泛词"），产出越可控。

**真实例子**（子代理实跑产出 · 节选）

把同一份需求整个换到小红书场景，占位符也随之换成 `{{笔记主题}}` / `{{目标人群}}`：

```markdown
# Role：小红书爆款笔记生成助手

## Rules
1. 标题长度 ≤20 字，且包含 {{笔记主题}} 或 {{目标人群}} 的关键词
2. 正文第一段第一句为钩子句，≤30 字，从"痛点陈述 / 反常识结论 / 数字承诺"三选一
3. 正文 3–6 段，每段以 1 个 emoji 开头，全文 300–600 字
4. 文末输出 3–5 个 #话题标签，每个 ≤10 字
5. 全文不出现"最、第一、国家级、顶级、绝对、全网、100%"等极限词与平台违禁词
```

注意第 5 条——**平台规则变成了可判定句**，模型照做就能自查，而不是"注意合规"这种空话。

### 场景七：模糊想法 → 结构化提示词（从零生成）

- **触发**："我想做个帮人改简历的 AI 助手，帮我写成提示词"。
- **技能动作**：基于你的想法补全角色、技能、目标、工作流、约束，落成 LangGPT 骨架。
- **你得到**：一份可直接用的结构化提示词。
- **提示**：给一点背景（给谁用、做什么、在哪用）会显著更好。

**真实例子**（实跑记录 · 本次就是你提的这个问题）

你只说了一句：**"我想做个帮人改简历的 AI 助手，帮我写成提示词"**。
技能先收口两个问题（目标场景 → 你选"国内社招通用"；工作方式 → 你选"先诊断再改写"），
然后落成骨架（节选）：

```markdown
# Role: 中文社招简历诊断与改写顾问
## Profile
- target_audience: 在中国大陆投递社招岗位、已有 1 年以上全职工作经历…；
  不含在校学生、应届生与校园招聘候选人
## Workflows
- 步骤 3: 七维体检（岗位匹配度、时间线连续性、职责与成果配比、数据支撑率、
          关键词覆盖、信息密度与版式、事实一致性），每个维度带可计数阈值
```

一句话 → 96 分终稿的差距，全靠收口时那两个问答。

### 场景八：长提示词 / 从文件优化

- **触发**："优化 prompt.txt 里的提示词" / 直接粘贴很长一段。
- **技能动作**：提示词较长时，可直接把内容交给技能；也可从文件读取后优化。
- **你得到**：同场景一。
- **提示**：超长提示词建议先说明"重点优化哪部分"，避免被篇幅稀释。

**真实例子**（对本次 25113 字节终稿实跑的两个检查）

```text
$ optimize_cli.py vars  "@简历改写助手_系统提示词.md"
["目标岗位JD", "简历原文"]          ← 两个中文占位符完整保留（G9）

$ optimize_cli.py lint  "@简历改写助手_系统提示词.md"
PASS：无互斥约束                    ← 没有自相矛盾的约束（G7）
```

长提示词最容易出现"改着改着把占位符丢了"或"前后两条约束打架"，这两个检查专治此病。

### 场景九：给现有提示词打分

- **触发**："这个提示词能打几分" / "评估一下这段 prompt 的质量"。
- **技能动作**：跑评分接缝（0-100，确定性规则器）。
- **你得到**：分数 + 诊断（哪些地方拉低了分）。
- **注意**：分数是结构 / 具体性维度的启发式评分，不是真 LLM 评测，用于横向比较足够，不宜当绝对指标。

**真实例子**（实测）

```text
$ optimize_cli.py evaluate "@raw_resume_coach.txt"             → 70.0
$ optimize_cli.py evaluate "@简历改写助手_系统提示词.md"        → 96.0
```

⚠ 提醒：如果一篇明显写得更好的稿子分数反而暴跌，多半是规则器误伤
（比如提示词里写"禁用词：一些、尽量…"会被当成"用了模糊词"）——**该修的是规则器，不是稿子**。

### 场景十：作为大任务的子步骤

- **触发**："先优化这个 agent 的 system prompt，再用它写代码"。
- **技能动作**：优化作为流程的一环被调用，产出优化提示词后交回主任务。
- **你得到**：下游任务拿到的是"已优化"的提示词。
- **适用**：agent 构建、评测脚本、自动化流水线等。

**真实例子**（本次交付前做的验收）

把终稿提示词直接当作 system prompt 驱动一个子代理，喂进一份虚构简历 + 一份 JD，
实际拿到的输出（摘录）：

```text
步骤 1  累计月数 = 55 + 16 = 71 个月 ≥ 12 个月 → 边界核验通过
步骤 3  维度2 时间线连续性：缺口 5 个月 > 3 个月 → 处数 1 → 不达标
        维度4 数据支撑率：含可核验数字的 bullet 0 ÷ 9 = 0% < 60% → 不达标
步骤 4  Q3｜缺失事实：效率提升的前后值与分母
        默认处理方案：A（不写数字）→ 改用"可核验事实 + 明确范围"
```

**这一步才是真正的验收**——分数 96 和门禁全绿都发现不了"照做会撞墙"的问题，
只有拿真实输入跑一遍才知道提示词能不能落地。

## 4. 一个完整走查示例

原始（口语化、含模糊词）：

> 帮我写一些关于产品推广的内容，尽量吸引人，发在社交媒体上，大概写几个版本。

**实测诊断**（`optimize_cli.py analyze`，非杜撰）：7 条问题，得分 **20**。

```
含模糊词「一些」「几个」「大概」「尽量」，建议量化为具体可执行标准
缺少角色 / 身份设定（建议用 LangGPT 风格明确 # Role）
缺少明确的执行步骤 / 工作流
缺少输出约束（格式、边界、禁忌）
```

技能动作：诊断 → 改写（LangGPT 结构）→ 评分（**20 → 88**，实测）→ 对比（after 胜出 **+68**）。

优化后（节选）：

```markdown
# Role: 社交媒体增长文案专家
## Goals
- 产出 3 个社媒版本，分别面向年轻女性种草 / 性价比党 / 泛人群破圈
## Constraints
- 每段 ≤120 字；不用"震撼"等空泛词
- 必须给出可量化利益，禁止编造数据
- 输出格式：版本一/二/三，各含【平台】【钩子】【正文】【标签】
```

完整对照见技能内 `examples/before_after.md`。

## 5. 可视化报告：回看每一轮改了什么（v2.2）

只想看结果时不用管它；想**追责 / 复盘 / 确认子代理到底做了什么**时，让 WorkBuddy
打开 `runs/<ts>/report.html`（零依赖单文件，双击也能开）。里面五块：

| 区块 | 你能看到什么 |
|------|-------------|
| 总览 | 盲评质量分轨迹（LLM-as-judge · 0-100，唯一对外分数）、诊断问题数轨迹（收敛=清零）、G1–G10 门禁逐项、结论徽标 |
| 每轮改进 | 分数与字符变化、**改前→改后的逐行 diff**、这轮要落实的指令、**改进评价**、已消除与新增的问题 |
| 独立盲评 | 每次盲评的评分、优点 / 缺点、blocking_conflicts、修改指令 |
| 运行跟踪 | 每轮**可复制复跑的脚本命令**、**交给子代理的任务卡原文**、**子代理产出原文**、任务卡→产出的时间间隔 |
| 原文 / 终稿 | 两版全文对照 |

**改进评价**是脚本按规则判的，不是模型拍的：

- 有效改进 —— 问题清零（且有消减）
- 改进 —— 问题减少但没清完
- **空转** —— 问题清单无变化（第 2 轮幂等属正常现象）
- **引入新问题** —— 问题不减反增；若同时冒出模糊词，报告会提示"先查规则器假阳性，别急着改稿"

## 6. 使用建议 / 最佳实践

1. **给足上下文**：领域、受众、平台、硬约束说得越清楚，改写越贴身。
2. **先诊断后改写**：不确定问题在哪时，先走场景二体检，再决定怎么改。
3. **善用对比验证**：改完用场景三确认"真的变好了"，再落地。
4. **复杂就迭代**：一次不到位用场景四多轮打磨。
5. **创意变体用子代理**：要新角度用场景五，拿到后人工过一遍。
6. **约束写可判定句**：把"友好一点"改成"用第二人称、句长 ≤20 字、不用感叹号"。
7. **交付前拿真实输入跑一遍**：分数和门禁都是下限，只有真实用例能验出
   "照做就撞墙"的问题（例如要求写 5–7 句又限死 60 字）。技能会做，你也可以再做一次。
8. **要复盘就开可视化报告**：想看某一轮到底改了什么、子代理当时拿到什么任务卡，
   直接让 WorkBuddy 打开 `runs/<ts>/report.html`。

## 7. 局限与注意

- **诊断 / 评分是规则器（零 LLM）**：基于模糊词表与结构特征，适合横向比较与快速体检，
  不是权威评测。**分数暴跌但内容明显变好时，多半是规则器误伤**（例如提示词里写
  "禁用词：一些、尽量…"会被当成"用了模糊词"），此时该修的是规则器，不是稿子。
- **门禁全绿 ≠ 验过了**：分数与 G1–G10 只是**下限**。真正的验收是拿一个真实输入
  跑一遍终稿——技能在交付前必须做这一步，你也可以自己再做一次。
- **改写与盲评都由独立子代理执行**：主代理只做编排（渲染任务卡、spawn 子代理、传文件），
  不代写、不打分——这保证了评审独立性与上下文纯净；代价是每轮会多消耗子代理调用。
- **脚本不能自证"产出是谁写的"**：脚本只渲染任务卡并退出，子代理由主代理 spawn。
  v2.2 起会留痕"任务卡→产出的时间间隔"（过短会告警），可证明中间确有工作发生，
  但**不能证明执笔者**；真正的独立性看 Agent 调用记录与报告里的留痕。
- **改写是生成式**：由子代理产出，质量随模型与约束而变，请人工确认。
- **不调用任何外部 LLM SDK**：整个流程在 WorkBuddy 内闭环，无需 API key。
- **产出是提示词文本**：技能交付优化后的提示词，你需要把它粘贴到目标系统使用。
- **已结构化输入幂等**：把优化结果再丢给技能，不会被无谓嵌套。

## 8. 它和"脚本"的关系（一句话）

技能底层确实带了一套 Python 确定性引擎（`scripts/`），但**你不用碰它**——
正常交互就是"把需求说给 WorkBuddy"。你唯一可能想主动要的产物是
**`runs/<ts>/report.html` 可视化报告**；只有当你想批量 / 自动化调用时，才需要看
`references/workflow.md` 了解引擎契约。本篇文档聚焦"用技能"，不展开脚本命令。
