## F. 元教训（写给未来的我）

1. **自己写的仪器只证明自己想验的东西**——必须主动构造反例打自己的工具（A1 就是这么发现的）。
2. **规则引擎抓不住语义矛盾**：结构分 96 与垃圾稿同分。
3. **"提醒型"文字挡不住复发**，只有退出码能挡。（2026-10-10 延伸：changelog 也不能只躺在文档里——E9/E15/E16 修复后回归长期空白，直到 `partE` 补上才重新被退出码看守。）
4. **用户看不见 = 没发生**：过程必须播报，断言必须可复现。
5. 本技能的正确用法：规则引擎当下限 → 门禁防退步 → 子代理盲评当第二双眼睛（E18 后兼当质量阈值）→ **真实用例做最终验收**。缺哪层，那层的洞就漏过去。
6. **分数下降先怀疑仪器，不要先改稿**。两次 96→76 / 70→26 都是规则器假阳性（A7/A8），改稿只会毁掉已经正确的内容。判据：分数暴跌而内容明显变好 = 仪器错。
7. **盲评的边际收益递减，且会自我膨胀**：同一命题 4 次盲评分别抓出 5 / 2 / 1 / 0 条 blocking_conflicts。必须给 judge 划定"什么不算阻塞"，否则永远收敛不了（E8）。
8. **PASS 不等于验过了**：G9 曾因正则只认 ASCII，7 轮"变量完整 PASS"全是假 PASS（A9）。**看到门禁全绿时，先问一句"这个检查真的跑了没有"**——空转的检查比没有检查更危险。
9. **KNOWN_ISSUES 自己也会过期**：A1 的"实测 exit 0"后来变成 exit 1；"已修复"的 E9/E15/E16 一度没有任何回归在看守。**清单里的"证据"与"已修复"都要定期重跑验证**——这和 F.1 是同一件事，只是对象换成了这份文档本身。
